## 2. Separate A from B

**A -- conditional physical containment:** genuine parent membership in the intended outer+inner chain, supported nested-Job semantics, no relevant breakaway permission, valid effective limits and trusted ownership/lifetime provide documented creation-time inherited scope. This is conditional OS enforcement, not a measurement of actual exit.

**B -- exact evidence/custody:** for reliable successful creation, or an interrupted invocation with a potentially created but unknown child, another living authorized owner must have a discoverable valid handle to THAT process and the required retained exit evidence. A kernel reference whose handle value is lost is not usable custody. Producer handles/PID absence/normal-role exits/Job-kill requests are not substitutes.

A does NOT imply B. Failure to prove B does NOT prove escape or refute A. Under genuinely established no-breakaway premises, simply assuming escape is not a valid counterexample to inheritance. Conversely, intended flags and fail-closed status do not establish unknown runtime membership or physical safety.

Known complete native FALSE is the separate API-level negative-control outcome under E1-E7; it does not require fabrication of a child handle/exit or imply that no transient kernel object ever existed. The unresolved B question concerns successful or interrupted creation, not inventing an object on every reliable rejection.

## 3. Documented OS support, source premises and unknowns

- Job Objects / Nested Jobs document default CreateProcess association with every Job in the parent chain. Breakaway stops at the first prohibiting Job. No-breakaway membership is creation-time inherited containment, not merely post-return AssignProcessToJobObject.
- The explicit CREATE_BREAKAWAY_FROM_JOB probe is NOT the ordinary probe. The flag requires policy permission for escape; nested parent policy matters. Do not infer either actual escape from a TRUE result or a complete FALSE/error-code table from these pages. Codes5/1816 are nonexclusive, not sole-cause proof.
- Job limits/readback apply to the declared Job scope. Active3 is not an all-time guarantee that no fourth intermediate kernel OBJECT can ever be allocated before rejected association. The documented active-limit association failure can terminate the affected process. Aggregate commit is not RSS or historical peak equality.
- TerminateJobObject covers currently associated processes and descendant Jobs; KILL_ON_JOB_CLOSE acts when the last relevant Job handle closes. Neither statement supplies an independently observed exact probe-exit record or complete interrupted-call rollback theorem.
- CreateProcessW returns PROCESS_INFORMATION on success and can return before child initialization finishes. The reviewed documentation does not specify every internal outcome if its caller is killed during the call. No guaranteed late child, guaranteed complete rollback or durable surviving receipt is inferred.

## 6. Architecture variants: documented parts are not a full B proof

### 6.1 Worker-origin JOB_LIST

**API/platform:** PROC_THREAD_ATTRIBUTE_JOB_LIST requires Windows10/Server2016+ and ordered valid Job handles, an initialized/live attribute list, STARTUPINFOEX and EXTENDED_STARTUPINFO_PRESENT. It is a different request from the current no-attributes variant. Attribute/list/rights failure cannot masquerade as evidence for the old breakaway negative control.

**Caller/meaning/ownership:** caller remains the already outer+inner worker, which owns neither usable Job handle. Making such handles usable would require a legitimate transfer, not copying foreign numeric values. Transferring INNER creates another Job owner and can defeat the reviewed controller-last-close fallback; transferring OUTER changes observer-last-close assumptions. Valid nesting/order and the combination with BREAKAWAY must be reviewed, not assumed.

**Death/custody:** creation-time association may be useful, but ordinary inheritance already supplies it conditionally. JOB_LIST does not assign returned PROCESS custody to an independent observer or define every caller-death rollback. It therefore does not by itself satisfy B.

**Resources/time:** no extra program is inherently required, but handle/buffer/setup/ABI work and altered ownership must fit active3/active2 and the same2GiB/96MiB/120s. No such complete proof or measurement exists. Not recommended as a ready architecture.

### 6.2 Keep worker producer; strengthen PROCESS handoff

**API/support:** DuplicateHandle can transfer a PROCESS to the existing observer with query/synchronize/terminate rights and no INNER Job export. This preserves the original caller and negative-control meaning. Current code does this after return.

**Death/custody:** faster IPC, a shared receiver-discovery slot, or an observer-initiated pull could reduce a post-duplication/publication interval only after a reviewed pointer/identity/ordering protocol is provided. Writing native output into shared storage is not automatically a completed trustworthy receipt. A raw CreateProcess PROCESS_INFORMATION contains caller-process handle values, not magically valid observer handles. A producer dying during CreateProcess or before any usable transfer still defeats the claimed all-interval B proof.

**Resources/time/lifetime:** an existing-role PROCESS-only transfer need not add an actor or keep INNER alive; it still needs rights, bounded mappings and target-handle lifetime. More polling/ACK/setup consumes the same120s and cannot hold STOP hostage. No full variant is shown feasible; this is not a source implementation task.

### 6.3 Move creation to controller or observer / replacement parent

A controller caller is already outer+inner-bound and owns INNER; an observer caller is OUTER-only and must not become an extra INNER member. Quietly adding the observer to the nominal controller+worker INNER would conflict with active2 and alter scope. An observer-origin probe is not the same test of worker-origin inherited active2/no-breakaway policy.

Either role may receive original creation handles if it calls CreateProcess, but producer death is now death of that role. The same native-call-to-surviving-handoff interval has not disappeared; retaining the PRODUCER process does not retain its child handles. A replacement-parent attribute changes inherited token/quotas/Job context without automatically moving returned PROCESS_INFORMATION to that parent. It is not custody by declaration.

Counts could stay within15+2 only if exactly the same actors/attempts are reused, but caller/context semantics, last-close, IPC and runtime costs change. No source variant demonstrates full B within the2GiB/96MiB/120s limits. No extra controller, observer or restart is approved.

### 6.4 Block producer death/STOP until a handoff ACK

This is NOT an admissible solution. Making STOP/termination wait for CreateProcess, DuplicateHandle, actor queue, writer or ACK reintroduces the prohibited liveness dependency and conflicts with frozen L01 and G04. A short polling target or a finally block is not a survival theorem. It adds no process, but violates the control contract and cannot claim an unaffected120s budget.

### 6.5 Recover by Job enumeration/notifications or add supervision

Existing IOCP NEW_PROCESS messages and PID sets are discovery hints, not exhaustive exact-object/exit history. Fast exit, delayed notification, PID reuse and failed OpenProcess leave B unresolved. Empty outer lists and normal-pair exits cannot certify an unidentified probe.

No reviewed debugger/ETW/service/kernel mechanism supplies the demanded all-interval guarantee here. Adding a helper/observer outside scope violates the no-unmetered-process rule; using a new in-scope mechanism still requires source, semantic, memory and timing proof, not an assumption of free observation. No such design or new process is recommended.
